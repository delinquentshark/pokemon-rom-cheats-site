Wishes of Tomorrow Field Guide

Cheat codes for the Pokémon ROM hack Wishes of Tomorrow, worked out from the game itself and tested in the mGBA emulator, plus look-ups for items, species, moves and wild encounters.

Using a code in mGBA

  1. Open the cheats window. With the game running in mGBA, pick Tools → Cheats…
  2. Paste it and add it. Press Copy on a code in this guide, paste it into the box that says Enter codes here… and click Add New Code. Leave the code type on Autodetect.
  3. Tick it on, untick it off. A new code starts ticked, so it's already working. Untick it to switch it off. Double-click its name, (untitled), to rename it.

Before you start

  • Check it's the right game file. In mGBA, with the game running, open File → ROM info…: CRC32 should say 5fff1cc3. Anything else is a different version of Wishes of Tomorrow: the codes won't work and could crash the game.
  • Back up your save. Copy the .sav file next to your ROM somewhere safe before trying codes. Every code here was tested for save damage, but a backup costs nothing.
  • Add each code on its own so you can switch them on and off separately. Don't add a "master code": mGBA doesn't need one, and one made for another game stops these codes working. If you already added one, remove all your cheats and restart mGBA.
  • Codes only work while they're ticked. Whatever you get while one is on (items, money, Pokémon, moves) is normal game data, so it stays after you untick the code and save.
  • Untick a code before you remove it. If you press Remove on a code that's still ticked, its effect can keep running until you restart mGBA.
  • mGBA remembers your codes, and whether each one is ticked, the next time you open the game. Untick the ones you aren't using.
  • Your game file is never changed. Codes change the game only in mGBA's memory, and only while they're ticked.

How the codes were made and tested

Every code was worked out from this ROM: its code was disassembled to find where the game decides each thing (a Pokémon's shininess, the money in the save, the move a TM teaches…), and each code changes that spot, usually by patching one or two instructions in mGBA's copy of the ROM. Codes that change a new Pokémon change the values the game passes to its own creation routine, so the game still builds a valid Pokémon itself.

Every code was then run in a headless build of mGBA 0.10.5, driving the game like a player: walking into encounters, running the game's own event scripts, buying in a Poké Mart, winning battles, opening menus. After each test the result was read from the game's memory, and anything saved was checked by saving with the codes on, unticking everything, resetting and pressing Continue: the Pokémon, items and money had to come back unchanged, with a valid checksum, no Bad Egg, and the game loading straight into the overworld. Every code was also loaded as Autodetect and as Action Replay MAX (and its raw form as Autodetect) to check it writes exactly its patch and that unticking restores the original. The ROM file's SHA-1 was the same after all testing.

The details for each code, with the tables and screenshots, are in the Under the hood section at the bottom of its tab. Three checks cover every code at once:

Code formats

Encrypted
The codes you copy on this page are encrypted Action Replay (PAR v3) codes. mGBA reads them as Autodetect or Action Replay MAX.
Raw
Each code's raw (decrypted) form is in the Under the hood section of its tab, with the addresses it changes. Raw codes need Autodetect. Most are ROM patches: 00000000 18aaaaaa + 0000vvvv 00000000 puts the 16-bit value vvvv at address 0x08000000 + aaaaaa × 2.
In the browser
The page builds each code from your choices in codes.ts, a copy of the Python generator used for the tests. A check runs both on every code the page can make from a list (all species, natures, genders, TM and move pairs, and items) and on 3,025 party edits (every slot and field, the edge values, and 3,000 random mixes): 71,367 codes, 634,623 lines, and they match exactly. That check runs in Node.js. The page itself was tested in Chromium at desktop and phone widths, not in other browsers.
Master codes
mGBA doesn't need one. A vanilla Emerald master code hooks an address this hack doesn't use, and mGBA copies that hook into every cheat added after it, so those cheats never run.
Remove while ticked
Unticking a code restores the original instructions. Pressing Remove on a ticked code drops it from the list but leaves its patch in mGBA's memory until the game is reloaded or mGBA restarts.

Money, coins and Battle Points

Money (SaveBlock1 + 0x490) and coins (+0x494) are stored XOR'd with the save's key (SaveBlock2 + 0xAC), so a plain memory write can't set them. The codes change the game's own money and coin functions instead, and the game stores the maximum itself the next time it adds or takes some, key and all.

Money
GetMoney (0x081897A0) returns 999,999 (the literal already in AddMoney's pool at 0x08189804); IsEnoughMoney (0x081897C8) and special 0xC8 (0x08189824) always say yes; AddMoney (0x081897EC) and RemoveMoney (0x08189810) both branch to AddMoney's "cap at 999,999" store; special 0xC9 (0x08189850, take the cost in var 0x8005) returns at once.
Coins
GetCoins (0x080EED58) returns 9,999; AddCoins (0x080EEDA8) stores 9,999 and returns TRUE; RemoveCoins (0x080EEE0A) stores 9,999 and returns TRUE.
Battle Points
SaveBlock2 + 0xEB8, a plain u16 the game caps at 9,999. One type 0x42 line writes 9,999 there through gSaveBlock2Ptr (0x03005228) every frame.

Always shiny

00000000 180DB42D 00002301 00000000 00000000 1811FFA7 00002401 00000000

Patches 0x081B685A in the creation routine from adcs r3, r3 to movs r3, #1, so "is shiny" is always 1. The game stores that in its own shiny bit, outside the protected data. The personality value isn't touched, so nature and gender are unaffected.

The ice-lab starters decide their shininess on their own. Catch on the first ball

The ball-throw battle command (Cmd_handleballthrow, 0x080ACD12) first sends a ball thrown at a trainer's Pokémon to its own script (0x080ACD92), which blocks it. How each code works

Edit a party Pokémon

The ROM has a large empty area at the end (0xFF from 0x09C74F08). The code writes a small routine there, at 0x09FF8000, followed by a table: the species the code was made for (two bytes), the party slot, then (field, value) pairs, then 0. Its last two lines point the Start menu's POKéMON entry (the pointer at 0x08CF56B4, normally StartMenuPokemonCallback at 0x08210935) at the routine. So each time POKéMON is picked, the routine runs first: it reads the slot's species with the game's GetMonData and stops unless it's the one in the table (an empty slot reads as 0, so it never matches), skips an Egg, writes each field with the game's own SetMonData (which re-encrypts the Pokémon's data and fixes its checksum, so it stays valid), calls CalculateMonStats, then jumps to the real callback and the party screen opens as usual. Unticking restores the pointer, so the routine is never reached again.

EXP boost

After a battle, ApplyExperienceMultipliers (0x080AF520) works out each Pokémon's EXP and ends with exp = result + 1. The battle code then adds that to the Pokémon's EXP in one go (0x0805ADE8) and stores it in a 21-bit field: past 2,097,151 it would wrap around and the Pokémon would drop levels, and the game doesn't cap it. So the code does: the Exp. Charm's ×1.5 block (0x080AF5BE–0x080AF5D8) is replaced with the multiplier (a shift by 1, 2 or 3) and a cap at 457,151, and the final store (0x080AF61A) branches there. EXP is only given below level 100, where a Pokémon has less than 1,640,000 EXP (the most any growth rate needs), so even the maximum can't pass 2,097,151. Max loads 457,151 for every win.

Eggs hatch fast

Every 128 steps (cmp r3, #0x7F at 0x08102C08) the game takes one egg cycle off each Egg in the party (two with Flame Body), and an Egg with none left hatches. Fast makes that check pass on every step (cmp r3, #0), so an Egg hatches after about as many steps as it has cycles (Bulbasaur: 20). At once also sets the cycles straight to 0 (0x08102C50 and 0x08102C54), so it hatches on the second step.

How each code works

Change what a TM teaches

00000000 1837D876 0000MMMM 00000000

The game looks up each TM's move in a table at 0x086FB0EC, 2 bytes per TM and HM item (TM01 is item 582, HM01 is item 682). The first line of the code points at the chosen TM's 2 bytes and the second line is the move ID to put there. While the code is ticked, mGBA writes that move ID into its copy of the game in memory; when you untick it, mGBA puts the original 2 bytes back. The Bag, the party menu and the teaching all read that one entry (through 0x081A2F1C), which is why they all change together. The Bag's description text is stored separately, so it stays the TM's own. The .gba file on disk is never touched.

MMMM is the move's 4-digit hex ID from the list; the first line depends on the TM picked in the card. Use IDs 0001–034F (Pound to Malignant Chain). Higher IDs are Z-Moves and Max Moves, which nothing in the game teaches.

Any Pokémon can learn any TM

00000000 180CDD2C 0000E004 00000000

Before teaching a TM or HM, the game checks whether the move is in the Pokémon's own teachable list (0x081B9DF0) and stops with "not compatible" if it isn't. The code changes the 2 bytes of the branch after that check, at 0x0819BA58 (bne to b), in mGBA's copy of the game in memory, so the answer is ignored. No species' list is edited, and unticking puts the original branch back. The checks for an Egg and for a move the Pokémon already knows still work. The move tutors in this ROM pick the Pokémon on a PC-style screen that does its own check, so they're unaffected.
