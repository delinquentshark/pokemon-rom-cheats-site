Origin HeartGold Field Guide

Cheat codes for the Nintendo DS Pokémon ROM hack Pokémon Origin HeartGold (v4.0 Special Edition, English translation), worked out from the game itself and tested in the melonDS emulator.

Using a code in melonDS

  1. Open the cheat editor. With the game running in melonDS, pick System → Setup cheat codes.
  2. Paste it and save it. Click New AR code, type a name in Name, press Copy on a code in this guide and paste it into the Code box, then click Save.
  3. Tick it, then close. Tick the box next to the code's name in the list on the left, then click Close. (The Enabled box above the code doesn't stay ticked when you save.)
  4. Switch cheats on. Pick System → Enable cheats. If it was already ticked, pick it twice, off and on again: melonDS only reads your codes when cheats are switched on or the game starts. Do the same after you untick or delete a code.

Before you start

  • Check it's the right game file. In melonDS, with the game running, open System → ROM info: Game code should say IPKJ and ARM9 size 1117496 bytes, and the title screen should say Origin HeartGold. Anything else is a different version of Origin HeartGold: the codes won't work and could crash the game.
  • Back up your save. Copy the .sav file next to your ROM somewhere safe before trying codes. Every code here was tested for save damage, but a backup costs nothing.
  • Add each code on its own so you can switch them on and off separately. You don't need a "master code": melonDS doesn't use one, and these codes were tested without one.
  • Codes only work while they're ticked and cheats are on. Whatever you get while one is on (items, money, Pokémon) is normal game data, so it stays after you untick the code and save.
  • After adding, ticking, unticking or deleting a code, switch cheats off and on (System → Enable cheats, twice). Until then melonDS keeps running the codes as they were. Switching Enable cheats off stops every code at once.
  • melonDS remembers your codes, and whether each one is ticked, in a .mch file next to your game, and it remembers whether Enable cheats is on. Untick the ones you aren't using.
  • Your game file is never changed. Codes change the game only in melonDS's memory, and only while they're on.

How the codes were made and tested

Every code was worked out from this ROM: its code (the ARM9 program and its overlays) was disassembled to find where the game makes a new Pokémon, keeps your money and fills your Bag, and each code changes the game at that spot. Codes that change a new Pokémon don't rewrite it afterwards: they copy a small routine of their own into a free part of the DS's memory and point the game's own creation function at it, so the game still builds a valid Pokémon itself (its checksum, stats and ability). Each routine checks every frame that its code is still on, so a code stops acting as soon as you switch it off.

Every code was then run in melonDS 1.1 (a headless build of melonDS's own core), driving the game like a player: walking into wild battles, picking a starter in Professor Oak's lab, battling the rival, buying in a Poké Mart, opening the Bag, throwing Poké Balls. After each test the result was read from the game's memory, and anything saved was checked by saving with the codes on, switching every code off, turning the game off and on and pressing Continue: the Pokémon, items and money had to come back unchanged and valid, with the game back in the overworld. Every code was also loaded through melonDS's own cheat-file reader to check it writes exactly what it should. The ROM file's SHA-1 was the same after all testing. The steps in Using a code in melonDS were checked in the real melonDS 1.1 program.

The routine
The first lines (E23D0200 00000040 and the eight after it) copy a 64-byte routine into free memory at 0x023D0200. The two 1… lines point the call that builds a Bag screen (Bag_CreateView at 0x02076CC6, which calls BagView_New) at the routine. Each time the game opens the Bag, the routine asks the game's own Bag_GetQuantity how many you have and adds the rest with the game's own Bag_AddItem, the function picking up an item uses, so the item lands in its own pocket the normal way. Bag_AddItem adds nothing when the pocket has no free slot, or when the total would pass 999 (99 for TMs and HMs).
Still on?
The four D… lines before the last copy the game's frame counter (gSystem.vblankCounter, 0x021D00C0) and the item and quantity into a small table at 0x023D0340, every frame. The routine adds nothing unless that copy is less than 9 frames old, so once the code is off it stops, even though the call stays pointed at it until the game is reset.
Free memory
0x023C2000–0x023DFFFF is the end of the DS's main memory arena, above every heap the game makes; the game takes memory from it only while it starts up. Watched across start-up, menus, the Bag, battles and saving, nothing reads or writes 0x023D0000–0x023D03FF but these codes.
Items
768 items with a name, from the item data (a/0/1/7: 34 bytes per item; its pocket in the bits 7–10 of the halfword at +8) and the item names (message file 219). TM moves: TMHMGetMove (0x02076688) and its two tables, 0x020FFFF8 (TM01–TM92 and the HMs) and 0x020FFFAC (TM93–TM130, this hack's own).

Money, coins and Battle Points

Gen 4 games keep money and coins as plain numbers in the save data, so these codes simply write them. The save data moves around in memory, so the money and coin codes follow its pointer (0x021D11B4) every frame.

Money
621D11B4 00000000 "if the pointer is set", B21D11B4 "follow it", 00000088 VVVVVVVV write the amount at +0x88. This ROM caps money at 9,999,999 (PlayerProfile_AddMoney), not vanilla HeartGold's 999,999.
Coins
The same, writing 50,000 (the Coin Case's limit) as 16 bits at +0x94.
Battle Points
The Battle Frontier data the game keeps in memory at 0x021D1B2C and copies into the save when you save: 121D2480 0000270F writes 9,999 (the cap) at +0x954.

Under the hoodHow the catching codes work in memory, and how they were tested

How each code works

The codes are plain Action Replay DS lines; the raw form is the code itself. For the codes that come in versions, the one shown is the version picked at the top of this tab. The highlighted value is the one you'd change.

The routine every catching code shares

The six codes for new Pokémon all start with the same lines: E23D0000 000001BC and the 56 after it copy a 444-byte routine into free memory at 0x023D0000 (see "Free memory" on the Items tab), and the next two lines point two calls inside the game's CreateBoxMon (0x0206D158), the function that builds every new Pokémon, at it: the call that stores the personality value (0x0206D188) and the one that stores the ability slot (0x0206D344).

The routine has to know which Pokémon to change. Every function that makes a Pokémon passes CreateBoxMon a "fixed IVs" value, and 32 means "random IVs". The lines inside 52247D44 F9BCF625 … D0000000 (only while the field overlay that makes wild Pokémon is loaded, 0x02247D44 checked unchanged) change that 32 to 33 in the four calls that make wild Pokémon (0x02247D3A, 0x02247E50, 0x02247E9C, 0x02247EE2), and the line after them changes it to 34 in GiveMon (0x020533B8), which the lab script uses to give the starter. Any value of 32 or more still means "random" to the game. The routine turns 33 and 34 back into 32 (or 31, "all perfect", with Perfect IVs on), and only acts on Pokémon that came with one of them, so Pokémon made by any other call, such as trainers' Pokémon, are left alone.

Each code's last D9…/D6…/D5…/D6… lines copy the frame counter and the code's choice into its own 8 bytes of a table at 0x023D0300 every frame: the shiny code into slot 0, IVs 1, nature 2, gender 3, ability 4, species 5. The routine uses a choice only if its copy of the frame counter is less than 9 frames old, so a code you switch off stops acting at once, even though the calls stay pointed at the routine until the game is reset. The table's 000M (the low half of the D5000000 line) says which Pokémon the code covers: 1 wild only, 3 wild and the starter.

The capture routine in the battle overlay checks "is it a Master Ball?" at 0x0222B0C0 (beq), and a Master Ball skips the shake rolls. The patch lasts until the battle overlay is unloaded at the end of the battle.
